# Repeated verification study

Run from the project root:

    node research/reusable-kyc/study.mjs study-results

Defaults: five fresh service/chain runs, delays 0/25/75 ms each way, concurrency 1/8, 24 measured verifications per condition, four warmups per condition. This produces 1,440 measured attempts across 60 cells. RUNS and TRIALS can override sizes. The plan and environment are written before measurement, and each run file is updated after every cell. A final summary appears only after all runs complete. Preserve the output directory as an experiment artifact.

Each repetition starts a new local Hardhat node, deploys a new contract, generates new keys, and starts new service processes. Both backends receive the same workload pattern and synthetic assurance policy. Credentials are preissued and issuance is excluded from measurement. The experiment randomizes cell order with a saved deterministic seed.

## Delay and load definitions

Two HTTP proxy links are delayed: holder-to-verifier and verifier-to-status-service/RPC. Each proxy waits the configured delay before forwarding a request and before returning its response. Zero-delay conditions still traverse the proxies, so the baseline includes proxy overhead. No OS network settings are changed.

A verification involves a challenge request and a presentation request, followed by a fresh status check. Software holder signing is included. Requests generated by the RPC library are counted, including network checks. In this study only, chain RPC caching and batching are disabled to prevent incidental request reuse from masquerading as a fresh status check. Ordinary app settings remain unchanged.

Concurrency is the number of closed-loop workers, each starting another attempt after completing the previous one. Throughput is accepted verifications divided by batch wall time, including ramp-up and drain. It is not a capacity/saturation estimate. The client signs in the same Node process; this is not a population of real browsers.

## Outputs and interpretation

plan.json records the intended conditions and environment. run-N.json contains order, warmup failures, measured success/failure counts, all timings (including failed attempts), wall time, RPC traffic, and per-trial outcomes. summary.json reports the median of run medians, range of run medians, median run p95, and median successful throughput. Per-cell latency quantiles use successful attempts only, with failures explicitly reported alongside them; raw failed-attempt timings are retained.

The run is the repetition unit. Do not pool 120 same-condition requests and describe them as 120 independent system replications. Five repetitions are exploratory; min/max ranges are not confidence intervals. The report must retain warmup failures, timeouts, and failed attempts rather than silently dropping them.

## Limits

This injects application-layer delay, not realistic network emulation: no bandwidth limit, jitter, packet loss, asymmetric routing, congestion, or TLS. The chain automines locally and does not model public-network consensus/finality. Delay is not applied to issuance/revocation, and this study does not measure those operations or revocation propagation. CPU scheduling and all services share one machine. The custom credential format, simulated identity checks and software keys remain research limitations.
